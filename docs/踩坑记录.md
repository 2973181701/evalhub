## 阶段 0 · 环境与骨架

### 坑 1：MoonBit 装好了但 `moon` 命令找不到

**现象**
```
$ moon --version
bash: line 1: moon: command not found
```

**原因**：MoonBit 安装到 `C:\Users\<用户>\.moon\bin\`，但没有自动写进当前 shell 的 PATH。

**解法**：先确认安装位置，再显式加入 PATH：
```bash
ls ~/.moon/bin          # 应看到 moon.exe / moonc.exe / moonrun.exe
export PATH="$HOME/.moon/bin:$PATH"
moon version
```
**输出验证**：
```
moon 0.1.20260904 (94521db 2026-09-04)
moonc v0.10.12+1634b282e (2026-09-07)
moonrun 0.1.20260904
```

> 面试点：这说明 MoonBit 是「自包含工具链」（编译器 moonc + 运行器 moonrun + 包管理 mooncake 都在一起），不依赖系统编译器。

### 坑 2：`moon init` 不存在

**现象**
```
$ moon init --help
Error: no such subcommand: `init`, is `moon-init` a valid executable accessible via your `PATH`?
```

**原因**：这个版本把初始化拆成了独立可执行文件 `moon-init`，且安装包里没带它。

**解法**：用 `moon new` 代替：
```bash
moon new <目录> --user <用户名> --name <模块名>
```

### 坑 3：模块名不能写成 `evalhub/core` 路径形式

**现象**
```
$ moon new moontest --user chenshijie --name evalhub/core
Error: Project name evalhub/core contains invalid characters.
Names must match package id syntax: start with an ASCII letter or underscore,
followed by ASCII letters, digits, dashes, or underscores.
```

**原因**：`--name` 只接受**单个标识符**，`/` 是模块与包的**分隔符**，由工具自己拼。

**解法**：`--user` 和 `--name` 分开传，工具会拼成 `<user>/<name>`：
```bash
moon new moontest --user chenshijie --name core    # → 模块名 chenshijie/core
```

### 坑 4：配置文件换了名字（旧教程全是错的）

**现象**：按老文档找 `moon.mod.json` / `moon.pkg.json`，找不到。

**实际情况**（本版本 `rr_moon_mod` / `rr_moon_pkg` 特性已启用）：

| 老格式（已弃用） | 新格式（当前） |
|---|---|
| `moon.mod.json` | **`moon.mod`** |
| `moon.pkg.json` | **`moon.pkg`** |

`moon.pkg` 是一套小型 DSL（不是 JSON）：
```
import {
  "moonbitlang/core/json",
}

options(
  link: {
    "js": {
      "exports": ["eval_engine"],
      "format": "esm",
    },
  },
)
```

> 面试点：能讲「我踩过配置格式迁移的坑，并且会用 `moon -C <dir> fmt` 从旧 JSON 迁移」。

### 坑 5：`moon new` 会自动 `git init`，嵌套仓库会出事

**现象**：在 `evalhub/core/` 里直接 `moon new`，会生成 `evalhub/core/.git`，变成嵌套仓库，外层 `git add` 只能看到一个空目录（gitlink），代码提交不上去。

**解法**：在临时目录生成后拷进来，并删掉模板自带的 git 相关目录：
```bash
cd /tmp && moon new ehcore --user chenshijie --name core
cd /tmp/ehcore && rm -rf .git .githooks .github
cp -r /tmp/ehcore/. <项目>/core/
```

### 坑 6：JS 导出语法（最关键的一步）

**目标**：让 Node 能 `import` MoonBit 编译出来的函数。

**解法**：在**产出构件的那个包**的 `moon.pkg` 里写：
```
options(
  link: {
    "js": {
      "exports": ["eval_score", "ping"],
      "format": "esm",
    },
  },
)
```

**产物位置**：
```
core/_build/js/debug/build/src/src.js        ← ESM 模块（Node 直接 import）
core/_build/js/debug/build/src/src.d.ts      ← 类型声明（前端 TS 可用）
core/_build/js/debug/build/src/moonbit.d.ts  ← MoonBit 基础类型映射
```

生成的 JS 长这样（函数名被 mangle，但**导出名是干净的**）：
```js
function _M0FP310chenshijie4core3src4ping() { return "pong"; }
export { _M0FP310chenshijie4core3src4ping as ping, ... }
```

**Node 侧验证**：
```js
import { ping, eval_score } from './core/_build/js/debug/build/src/src.js';
console.log(ping());              // pong
console.log(eval_score('hello')); // {"input_len":5}
```

> 注意：`exports` 只对**本包**的构件生效，下游包再 export 是没用的——所以引擎函数必须定义在写了 `exports` 的那个包里。

### 坑 7：`Json` 类型在 `builtin`，但 `parse` 在 `@json`

**关键区分**（很容易搞混）：

| 东西 | 所在包 | 是否需要 import |
|---|---|---|
| `Json` 枚举类型 + 构造器 | `builtin` | **不需要**，自动可见 |
| `@json.parse` / `@json.to_json` / `@json.from_json` | `moonbitlang/core/json` | **需要** import |

`Json` 枚举的真实定义（`core/builtin/json.mbt`）：
```moonbit
pub enum Json {
  Null
  True
  False
  Number(Double, repr~ : String?)
  String(String)
  Array(Array[Json])
  Object(Map[String, Json])
}
```
→ **构造器首字母大写**，写 `Json::String(s)` 而不是 `Json::string(s)`（后者只在 `Json::string()` 工厂函数里合法）。

### 坑 8：`@json.parse` 会 raise，`?` 用不了

**现象**
```
Error: [4122] Function with error can only be used inside a function with error types in its signature.
Error: [3002] Parse error, unexpected token `?`
```

**原因**：签名是 `pub fn parse(StringView, max_nesting_depth? : Int) -> Json raise ParseError`——它**抛错**而不是返回 `Result`。而 `?` 运算符要求**当前函数签名里声明了 raise**。对外导出的纯函数又不能随便 raise（JS 侧接不住）。

**解法**：用 `try ... catch` 就地兜底，保证「引擎对外永远是纯函数、永远返回合法 JSON 字符串」：
```moonbit
pub fn eval_engine(input : String) -> String {
  let j = try @json.parse(input) catch {
    _ => return "{\"error\":\"parse failed\"}"
  }
  ...
}
```
**验证**：`eval_engine('{bad')` → `{"error":"parse failed"}`（不崩、不抛到 JS）。

> 面试点：这是「边界容错设计」——引擎是纯函数，输入垃圾也不能把宿主搞崩。

### 坑 9：`Json::value(key)` 已弃用

**现象**
```
Warning (deprecated): Suggestion: `if json is Object(obj) { obj.get(key) } else { None }`
```

**解法**：直接模式匹配，顺便把「类型不对」的情况一并处理：
```moonbit
fn get_str(j : Json, key : String) -> String {
  match j {
    Json::Object(m) =>
      match m.get(key) {
        Some(Json::String(s)) => s
        _ => ""
      }
    _ => ""
  }
}
```

# 阶段 1 · 评测引擎（5 维评分）

> 产出：`core/src/engine_eval.mbt`（引擎）+ `core/src/engine_eval_wbtest.mbt`（16 个单测）
> + `tools/engine_smoke.mjs`（Node 跨语言验收脚本）。测试 16/16 通过，Node import 链路验证通过。

### 坑 11：`String::charcode_at` 在本版本不存在

**现象**
```
Error: Type String has no method charcode_at.
```

**解法**：本版本取字符统一走迭代器 + `Char::to_int`：
```moonbit
fn codes_of(s : String) -> Array[Int] {
  let arr : Array[Int] = []
  for ch in s { arr.push(ch.to_int()) }
  arr
}
```
引擎内部全部用码元数组（`Array[Int]`）做文本计算，绕开 String API 的版本差异。
（备选：`String::get_char(i) -> Char?`、`String::iter2()`。）

> 面试点：把文本计算收敛到码元数组，API 变化只影响一个函数。

### 坑 12（本阶段最大坑）：`Json` 是「只读枚举」，不能用构造器造值

**现象**
```
Error: [4036] Cannot create values of the read-only type: Null.   // 写 Json::Null
Error: [4036] Cannot create values of the read-only type: String. // 写 Json::String(s)
Error: [4086] The labels repr~ are required by this function.     // 写 Json::Number(x)
```

**原因**：这版 `builtin` 里的 `Json` 枚举对外的构造器是只读的，官方给的是**小写工厂函数**。

**解法**（工厂函数在 `builtin`，无需 import）：

| 不要这样写 | 要这样写 |
|---|---|
| `Json::Null` | `Json::null()` |
| `Json::String(s)` | `Json::string(s)` |
| `Json::Number(x)` | `Json::number(x)` |
| `Json::Object(m)` | `Json::object(m)` |
| `Json::Array(a)` | `Json::array(a)` |

**但模式匹配仍然用大写构造器**，且 `Number` 的 `repr~` 标签在模式里要补 `..`：
```moonbit
match m.get(key) {
  Some(Json::Number(v, ..)) => v   // 不写 .. 会告警 missing_pattern_arguments
  _ => -1.0
}
```

> 面试点：「构造走工厂、解构走模式匹配」是这一版 MoonBit 的明确分工，文档还没跟上，靠编译器报错逐个试出来的。

### 坑 13：`Map::new()` 已弃用

**现象**
```
Warning (deprecated): Use `Map([], capacity=...)` instead
```

**解法**：`let m : Map[String, Json] = Map([], capacity=8)`，写入用 `m["key"] = value`（op_set），读取用 `m.get(key) -> Option`。

### 坑 14：真实数据的 reference 有两种形态，单一规则必翻车

**现象**：拿规则引擎直接跑 `prompts.json`，好答案得分反常：
- 代码题（C01）reference 是中文评分说明「函数应包含：…返回False、循环到sqrt(n)…」，
  一份正确 Python 代码按「全量要点命中」只得 2.0 分——大量中文说明文字根本不会出现在代码里；
- 创意写作题（W01）reference 是「15字内、贴合奶茶店、有吸引力」这种**元描述**，
  无论答案多好都无法和它做词面比对。

**解法**（按题型分流，规则可解释）：
1. **代码生成**：取「全量要点」与「纯 ASCII 标识符（False/sqrt/True…）」两种口径的**较高者**——
   代码标识符才是代码题可靠的机检信号；
2. **创意写作**：准确性与完整性直接给**中性分 3.0**——规则引擎不判主观质量，交给标注员，
   这恰好是平台 RLHF 人工环节存在的意义（面试可以正面讲这个取舍）；
3. 长要点二元组覆盖率阈值校准为 **0.45**：摘要题 S01 的合理改写答案实测覆盖率 0.47，
   0.6 会误杀。

> 面试点：评测引擎的分数不是「算出来的」是「校准出来的」——用真实数据集回归测试驱动阈值。

### 坑 15：刷字惩罚规则误伤代码缩进（跨层验证抓出来的真 bug）

**现象**：MoonBit 单测全绿，但 Node 验收脚本里代码回答的 expression 只有 2 分。
原因：「同一字符连续出现 ≥10 次判刷字」把代码的 12 格缩进空格当成了刷字，分数被砍到 2.0。

**解法**：刷字检测只统计**非空白字符**（空格/制表/换行不参与）。

> 面试点：单测覆盖不到的坑靠「第二入口」抓出来——引擎单测用的是短中文样例，
> Node 冒烟脚本塞了带缩进的真实代码。**跨层验证不是重复劳动。**

### 坑 16：测试专用的私有辅助函数要放进 `_wbtest.mbt`

**现象**：`get_num` / `parse_or_null` 只被测试用到，放在主源码里报 `Unused function` 警告。

**解法**：whitebox 测试与主包同 scope，直接把这两个函数定义挪进 `engine_eval_wbtest.mbt`，
主构建回到 0 警告。
