## 阶段 0 · 环境与骨架

### 坑 1：MoonBit 装好了但 `moon` 命令找不到

**现象**
```
$ moon --version
bash: line 1: moon: command not found
```

**原因**：MoonBit 安装到 `C:\Users\<用户>\.moon\bin\`，但没有自动写进当前 shell 的 PATH。

**解法**：先确认安装位置，再显式加入 PATH：
```bash
ls ~/.moon/bin          # 应看到 moon.exe / moonc.exe / moonrun.exe
export PATH="$HOME/.moon/bin:$PATH"
moon version
```
**输出验证**：
```
moon 0.1.20260904 (94521db 2026-09-04)
moonc v0.10.12+1634b282e (2026-09-07)
moonrun 0.1.20260904
```

> 面试点：这说明 MoonBit 是「自包含工具链」（编译器 moonc + 运行器 moonrun + 包管理 mooncake 都在一起），不依赖系统编译器。

### 坑 2：`moon init` 不存在

**现象**
```
$ moon init --help
Error: no such subcommand: `init`, is `moon-init` a valid executable accessible via your `PATH`?
```

**原因**：这个版本把初始化拆成了独立可执行文件 `moon-init`，且安装包里没带它。

**解法**：用 `moon new` 代替：
```bash
moon new <目录> --user <用户名> --name <模块名>
```

### 坑 3：模块名不能写成 `evalhub/core` 路径形式

**现象**
```
$ moon new moontest --user chenshijie --name evalhub/core
Error: Project name evalhub/core contains invalid characters.
Names must match package id syntax: start with an ASCII letter or underscore,
followed by ASCII letters, digits, dashes, or underscores.
```

**原因**：`--name` 只接受**单个标识符**，`/` 是模块与包的**分隔符**，由工具自己拼。

**解法**：`--user` 和 `--name` 分开传，工具会拼成 `<user>/<name>`：
```bash
moon new moontest --user chenshijie --name core    # → 模块名 chenshijie/core
```

### 坑 4：配置文件换了名字（旧教程全是错的）

**现象**：按老文档找 `moon.mod.json` / `moon.pkg.json`，找不到。

**实际情况**（本版本 `rr_moon_mod` / `rr_moon_pkg` 特性已启用）：

| 老格式（已弃用） | 新格式（当前） |
|---|---|
| `moon.mod.json` | **`moon.mod`** |
| `moon.pkg.json` | **`moon.pkg`** |

`moon.pkg` 是一套小型 DSL（不是 JSON）：
```
import {
  "moonbitlang/core/json",
}

options(
  link: {
    "js": {
      "exports": ["eval_engine"],
      "format": "esm",
    },
  },
)
```

> 面试点：能讲「我踩过配置格式迁移的坑，并且会用 `moon -C <dir> fmt` 从旧 JSON 迁移」。

### 坑 5：`moon new` 会自动 `git init`，嵌套仓库会出事

**现象**：在 `evalhub/core/` 里直接 `moon new`，会生成 `evalhub/core/.git`，变成嵌套仓库，外层 `git add` 只能看到一个空目录（gitlink），代码提交不上去。

**解法**：在临时目录生成后拷进来，并删掉模板自带的 git 相关目录：
```bash

cd /tmp/ehcore && rm -rf .git .githooks .github

```

### 坑 6：JS 导出语法（最关键的一步）

**目标**：让 Node 能 `import` MoonBit 编译出来的函数。

**解法**：在**产出构件的那个包**的 `moon.pkg` 里写：
```
options(
  link: {
    "js": {
      "exports": ["eval_score", "ping"],
      "format": "esm",
    },
  },
)
```

**产物位置**：
```
core/_build/js/debug/build/src/src.js        ← ESM 模块（Node 直接 import）
core/_build/js/debug/build/src/src.d.ts      ← 类型声明（前端 TS 可用）
core/_build/js/debug/build/src/moonbit.d.ts  ← MoonBit 基础类型映射
```

生成的 JS 长这样（函数名被 mangle，但**导出名是干净的**）：
```js
function _M0FP310chenshijie4core3src4ping() { return "pong"; }
export { _M0FP310chenshijie4core3src4ping as ping, ... }
```

**Node 侧验证**：
```js
import { ping, eval_score } from './core/_build/js/debug/build/src/src.js';
console.log(ping());              // pong
console.log(eval_score('hello')); // {"input_len":5}
```

> 注意：`exports` 只对**本包**的构件生效，下游包再 export 是没用的——所以引擎函数必须定义在写了 `exports` 的那个包里。

### 坑 7：`Json` 类型在 `builtin`，但 `parse` 在 `@json`

**关键区分**（很容易搞混）：

| 东西 | 所在包 | 是否需要 import |
|---|---|---|
| `Json` 枚举类型 + 构造器 | `builtin` | **不需要**，自动可见 |
| `@json.parse` / `@json.to_json` / `@json.from_json` | `moonbitlang/core/json` | **需要** import |

`Json` 枚举的真实定义（`core/builtin/json.mbt`）：
```moonbit
pub enum Json {
  Null
  True
  False
  Number(Double, repr~ : String?)
  String(String)
  Array(Array[Json])
  Object(Map[String, Json])
}
```
→ **构造器首字母大写**，写 `Json::String(s)` 而不是 `Json::string(s)`（后者只在 `Json::string()` 工厂函数里合法）。

### 坑 8：`@json.parse` 会 raise，`?` 用不了

**现象**
```
Error: [4122] Function with error can only be used inside a function with error types in its signature.
Error: [3002] Parse error, unexpected token `?`
```

**原因**：签名是 `pub fn parse(StringView, max_nesting_depth? : Int) -> Json raise ParseError`——它**抛错**而不是返回 `Result`。而 `?` 运算符要求**当前函数签名里声明了 raise**。对外导出的纯函数又不能随便 raise（JS 侧接不住）。

**解法**：用 `try ... catch` 就地兜底，保证「引擎对外永远是纯函数、永远返回合法 JSON 字符串」：
```moonbit
pub fn eval_engine(input : String) -> String {
  let j = try @json.parse(input) catch {
    _ => return "{\"error\":\"parse failed\"}"
  }
  ...
}
```
**验证**：`eval_engine('{bad')` → `{"error":"parse failed"}`（不崩、不抛到 JS）。

> 面试点：这是「边界容错设计」——引擎是纯函数，输入垃圾也不能把宿主搞崩。

### 坑 9：`Json::value(key)` 已弃用

**现象**
```
Warning (deprecated): Suggestion: `if json is Object(obj) { obj.get(key) } else { None }`
```

**解法**：直接模式匹配，顺便把「类型不对」的情况一并处理：
```moonbit
fn get_str(j : Json, key : String) -> String {
  match j {
    Json::Object(m) =>
      match m.get(key) {
        Some(Json::String(s)) => s
        _ => ""
      }
    _ => ""
  }
}
```

### 坑 11：`String::charcode_at` 在本版本不存在

**现象**
```
Error: Type String has no method charcode_at.
```

**解法**：本版本取字符统一走迭代器 + `Char::to_int`：
```moonbit
fn codes_of(s : String) -> Array[Int] {
  let arr : Array[Int] = []
  for ch in s { arr.push(ch.to_int()) }
  arr
}
```
引擎内部全部用码元数组（`Array[Int]`）做文本计算，绕开 String API 的版本差异。
（备选：`String::get_char(i) -> Char?`、`String::iter2()`。）

> 面试点：把文本计算收敛到码元数组，API 变化只影响一个函数。

### 坑 12（本阶段最大坑）：`Json` 是「只读枚举」，不能用构造器造值

**现象**
```
Error: [4036] Cannot create values of the read-only type: Null.   // 写 Json::Null
Error: [4036] Cannot create values of the read-only type: String. // 写 Json::String(s)
Error: [4086] The labels repr~ are required by this function.     // 写 Json::Number(x)
```

**原因**：这版 `builtin` 里的 `Json` 枚举对外的构造器是只读的，官方给的是**小写工厂函数**。

**解法**（工厂函数在 `builtin`，无需 import）：

| 不要这样写 | 要这样写 |
|---|---|
| `Json::Null` | `Json::null()` |
| `Json::String(s)` | `Json::string(s)` |
| `Json::Number(x)` | `Json::number(x)` |
| `Json::Object(m)` | `Json::object(m)` |
| `Json::Array(a)` | `Json::array(a)` |

**但模式匹配仍然用大写构造器**，且 `Number` 的 `repr~` 标签在模式里要补 `..`：
```moonbit
match m.get(key) {
  Some(Json::Number(v, ..)) => v   // 不写 .. 会告警 missing_pattern_arguments
  _ => -1.0
}
```

> 面试点：「构造走工厂、解构走模式匹配」是这一版 MoonBit 的明确分工，文档还没跟上，靠编译器报错逐个试出来的。

### 坑 13：`Map::new()` 已弃用

**现象**
```
Warning (deprecated): Use `Map([], capacity=...)` instead
```

**解法**：`let m : Map[String, Json] = Map([], capacity=8)`，写入用 `m["key"] = value`（op_set），读取用 `m.get(key) -> Option`。

### 坑 14：真实数据的 reference 有两种形态，单一规则必翻车

**现象**：拿规则引擎直接跑 `prompts.json`，好答案得分反常：
- 代码题（C01）reference 是中文评分说明「函数应包含：…返回False、循环到sqrt(n)…」，
  一份正确 Python 代码按「全量要点命中」只得 2.0 分——大量中文说明文字根本不会出现在代码里；
- 创意写作题（W01）reference 是「15字内、贴合奶茶店、有吸引力」这种**元描述**，
  无论答案多好都无法和它做词面比对。

**解法**（按题型分流，规则可解释）：
1. **代码生成**：取「全量要点」与「纯 ASCII 标识符（False/sqrt/True…）」两种口径的**较高者**——
   代码标识符才是代码题可靠的机检信号；
2. **创意写作**：准确性与完整性直接给**中性分 3.0**——规则引擎不判主观质量，交给标注员，
   这恰好是平台 RLHF 人工环节存在的意义（面试可以正面讲这个取舍）；
3. 长要点二元组覆盖率阈值校准为 **0.45**：摘要题 S01 的合理改写答案实测覆盖率 0.47，
   0.6 会误杀。

> 面试点：评测引擎的分数不是「算出来的」是「校准出来的」——用真实数据集回归测试驱动阈值。

### 坑 15：刷字惩罚规则误伤代码缩进（跨层验证抓出来的真 bug）

**现象**：MoonBit 单测全绿，但 Node 验收脚本里代码回答的 expression 只有 2 分。
原因：「同一字符连续出现 ≥10 次判刷字」把代码的 12 格缩进空格当成了刷字，分数被砍到 2.0。

**解法**：刷字检测只统计**非空白字符**（空格/制表/换行不参与）。

> 面试点：单测覆盖不到的坑靠「第二入口」抓出来——引擎单测用的是短中文样例，
> Node 冒烟脚本塞了带缩进的真实代码。**跨层验证不是重复劳动。**

### 坑 16：测试专用的私有辅助函数要放进 `_wbtest.mbt`

**现象**：`get_num` / `parse_or_null` 只被测试用到，放在主源码里报 `Unused function` 警告。

**解法**：whitebox 测试与主包同 scope，直接把这两个函数定义挪进 `engine_eval_wbtest.mbt`，
主构建回到 0 警告。

### 坑 17：`Json` 的布尔值没有 `Boolean` 构造器，模式匹配要写 `True` / `False`

**现象**：测试里写 `Some(Json::Boolean(b)) => b`，编译报「没有这个变体」。

**原因**：`Json` 枚举里布尔是**两个独立变体**，不是带参构造器：

```moonbit
pub enum Json {
  Null
  True        // ← 不带参数
  False       // ← 不带参数
  Number(Double, repr~ : String?)
  String(String)
  Array(Array[Json])
  Object(Map[String, Json])
}
```

**解法**：
- **构造**用工厂函数 `Json::boolean(x)`（收 `Bool`，返回 `Json::True` / `Json::False`）；
- **解构**只能匹配 `Json::True` / `Json::False`。

```moonbit
fn t_bool(j : Json, key : String) -> Bool {
  match j {
    Json::Object(m) =>
      match m.get(key) {
        Some(Json::True) => true     // 不能写 Some(Json::Boolean(b))
        _ => false
      }
    _ => false
  }
}
```

> 与坑 12 是同一类问题的两个面：**构造走工厂函数、解构走枚举变体**，而且不同变体的形态还不一致。

### 坑 18（排查最久）：单测失败，结果是测试自己解析错了对象

**现象**
```
test "annotators 列表按首次出现顺序输出" failed: `0 != 2`
```
引擎输出在 Node 里打印完全正确（`"annotators":["human","llm"]`），但测试里拿到的数组长度是 0。

**排查过程**
1. 先在测试里 `println` 引擎原始输出 → 完全正确，字段确实存在；
2. 再 `println` 解析后的对象 → 发现 `j` 打印出来是 **输入**（`{"records":[...]}`），不是输出！

**根因**：测试写成了

```moonbit
let j = t_parse(consistency_partial_json())        // ← 解析的是「输入构造器」
let ann = t_arr(j, "annotators")                   // ← 在输入里找 annotators，当然是空
```

而同一文件里其它用例写的是 `t_parse(consistency_engine(...))`（引擎输出），所以只有这一条挂。

**解法**：补上引擎调用，把「输入构造器」换成「引擎输出」。

> 面试点：测试挂了先怀疑**测试**，别急着改被测代码。定位手法是「打印中间态」——
> 把 `j` 直接 `println` 出来，一眼就能看出解析的是哪个对象。
> 这个坑也说明：**测试辅助函数（t_parse / t_arr）越通用，越容易掩盖「传错对象」这类错误**。

### 坑 19：小样本下不该硬算 Fleiss' κ

**现象**：只有 1 条「被全部标注者标注过」的样本时，κ 公式照样能算出一个数字——但这个数字没有任何统计意义。

**解法**：引擎在样本不足时**返回 `null` + 原因字符串**，而不是给一个假数字：

```moonbit
if annotator_count < 2 {
  return (None, "只有 1 位标注者，一致性无从谈起（κ 需 ≥2 人）")
}
if complete_n < 2 {
  return (None, "被全部标注者完整标注的样本不足 2 条，κ 无法稳定估计（当前 N 条）")
}
if 1.0 - p_e <= 0.0000001 {
  return (None, "所有标注者对所有样本的选择都落在同一类别，κ 无定义（P_e = 1）")
}
```

前端报告页把这句原因原样展示出来。

> 面试点：**宁可 null 不可编造**。数据标注岗最看重的就是「知道自己的数据能支撑什么结论、不能支撑什么结论」。

### 坑 20（真 bug，靠真实数据抓出来）：Unicode 下标导致参考答案判不中

**现象**：20 条真实回答跑完，`accuracy` 均分只有 **2.42**，明显偏低。抽查发现 K03 得 0 分：

| 项 | 内容 |
|---|---|
| 参考答案 | `H2O` |
| 模型真实回答 | `水的化学式是H₂O。这表示每个水分子由两个氢原子（H）和一个氧原子（O）组成。` |

模型输出用的是 **Unicode 下标字符 `₂`（U+2082）**，不是 ASCII `2`。字符级比对自然判「没命中」。
同类问题还有 `CO₂`（K02）。

**解法**：在文本进入引擎的**唯一入口** `codes_of()` 里做同形字符归一化——
下标/上标/全角数字 → ASCII 数字，全角括号 → 半角：

```moonbit
fn normalize_code(c : Int) -> Int {
  if c >= 0x2080 && c <= 0x2089 { return c - 0x2080 + 48 }   // ₀-₉ → 0-9
  if c >= 0x2070 && c <= 0x2079 { ... }                      // ⁰⁴-⁹ → 数字
  if c == 0x00B9 { return 49 }  // ¹
  if c == 0x00B2 { return 50 }  // ²
  if c == 0x00B3 { return 51 }  // ³
  if c >= 0xFF10 && c <= 0xFF19 { return c - 0xFF10 + 48 }   // 全角数字
  ...
  c
}
```

| 总分均分 | 3.74 | **3.83** |
| 事实问答类均分 | 3.68 | **4.18** |

**只归一化「同一个字符的不同写法」，不做任何语义猜测**——这是规则引擎的边界，不越界。

### 坑 22：curl 连不上 localhost，是系统代理在捣乱

**现象**
```
$ curl -s http://localhost:3000/api/health
upstream connect failed: 由于目标计算机积极拒绝，无法连接。 (os error 10061)
```
但同一个端口在同一个 shell 里刚启动的服务明明是活的。

**原因**：环境里配了 HTTP 代理，`curl` 默认把 `localhost` 也丢给代理，代理自然连不上。

**解法**（二选一）：
```bash
curl --noproxy '*' http://127.0.0.1:3000/api/health     # 方案 A：绕开代理
node -e "fetch('http://127.0.0.1:3000/api/health').then(r=>r.text()).then(console.log)"  # 方案 B：Node 原生 fetch
```
本阶段所有接口验收统一用**方案 B**（Node 22 原生 `fetch`），顺便也验证了后端代码用的同一条网络栈。

### 坑 23：业务规则绝不在两处实现（`/api/export` 计数对不上）

**现象**：后端 `/api/export` 返回 `total: 18, dropped: 0`，而引擎自己跑出来是 `total: 20, dropped: 2`。

**根因**：后端 store 层先自己 `.filter(choice !== '平手')` 过滤了一遍，再交给 MoonBit 数据引擎——
同一套「平手丢弃」规则在 JS 和 MoonBit 里各写了一份，`total` 就被吃掉了。

**解法**：后端**不做任何业务筛选**，把全部标注原样交给引擎，由引擎单点定义规则：

```js
// store.js —— 不筛选，规则只由 MoonBit 数据引擎定义
const items = annotations().map((a) => ({ id, task_type, prompt, answer_A, answer_B, choice: a.choice }));
return exportRlhf({ format, annotations: items });
```

修复后：`total: 20, exported: 18, dropped: 2, dropped_detail: {tie: 2, ...}` ✅

> 面试点：这是**分层架构最容易被破坏的地方**——网关层「顺手」做一点业务判断，
> 结果规则分叉、数字对不上。正确姿势是：**计算逻辑全部下沉到引擎，网关只做编排。**

### 坑 24：后台进程会随命令结束被杀掉

**现象**：`(node server.js &)` 启动后，同一次命令里的 `curl` 能通；命令一结束，下一次调用就连不上了。

**解法**：把服务放到**常驻后台任务**里启动（而不是在同一条命令里 `&`），
并且**改完后端代码要重启进程**——Node 不会热加载模块级状态（本次 `/api/export` 修复就踩了这个：
改完 store.js 后没重启，接口返回的还是旧结果，重启后立刻正确）。

### 坑 26：提交成功后的提示被「自动跳下一条」清掉了

**现象**：提交标注成功，但成功提示一闪就没（其实是被清了）。

**根因**：提交成功后自动跳到下一条未标注的题，而跳转会调用 `syncForm()`，
`syncForm()` 里有一句 `feedback.value = null`——刚设置的反馈被自己清掉。

**解法**：把反馈对象先存进局部变量，跳转之后再赋回：

```js
const fb = { type: 'ok', check: data.check, message: '校验通过，已入库' };
const next = items.value.find((i) => !i.annotation);
if (next) pick(next.id);   // pick → syncForm → feedback = null
feedback.value = fb;       // 跳完再落回
```

> 面试点：这是典型的**状态生命周期顺序**问题——「重置表单」和「展示结果」在同一串同步流程里，
> 谁先谁后决定了用户看不看得到反馈。

### 坑 27：雷达图不必上 ECharts

function xy(i, n, radius) {
  const a = -Math.PI / 2 + (i * 2 * Math.PI) / n;   // 从正上方开始，顺时针均分

# 阶段 5 · 收尾与 WASM 目标（P4 进阶项）

> 任务书 P4 原文：「进阶再 `moon build --target wasm`：满足 MoonBit『Wasm 优先』叙事，作为 P4 加分项」。
> 本节记录把这条做完的全过程——**三个坑都是真踩到的，不是设想出来的。**

## 坑 28：wasm-gc 默认产物是「空壳」，必须显式声明导出

**现象**：`moon build --target wasm-gc` 成功，产物 `src.wasm` 只有 **198 字节**。

**排查**：
```js
WebAssembly.Module.exports(new WebAssembly.Module(buf))   // → []
```
导出表是空的。198 字节的 wasm 里只有一个空的模块头。

**原因**：`moon.pkg` 里 `options(link: {...})` 只配了 `"js"` 目标，
wasm-gc 目标没有声明要导出哪些函数，编译器就把所有 `pub fn` 都当作「内部符号」——直接摇树摇没了。

**修复**：给 `moon.pkg` 补上 wasm-gc 的导出块。

```diff
 options(
   link: {
     "js": {
       "exports": ["version", "eval_engine", ...],
       "format": "esm",
     },
+    "wasm-gc": {
+      "exports": [
+        "version", "eval_engine", "annotate_engine",
+        "analyze_engine", "consistency_engine", "export_rlhf",
+        "abi_clear", "abi_push", "abi_len", "abi_read", "abi_run", "abi_version",
+      ],
+    },
   },
 )
```

**结果**：产物从 **198 字节 → 171.4 KB**，导出 12 个函数。

**验证**：`WebAssembly.Module.imports()` 返回 **0 个导入**——产物完全自包含，
不依赖任何 JS glue 或宿主函数。这一点很重要：说明引擎的「纯函数、零副作用」不是口号，
编成 WASM 后连一个外部符号都不需要。

> 面试点：`--target js` 和 `--target wasm` 的**默认导出策略不同**。
> JS 目标默认会把 `pub` 函数都挂到模块上；WASM 目标因为要摇树优化，必须显式声明导出。

## 坑 29：WASM 没有字符串类型，而 MoonBit 的「字符串」是**码点**序列（真 bug）

### 第一层：跨不过去

wasm-gc 产物能实例化了，但一调用就报：

```
TypeError: type incompatibility when transforming from/to JS
```

`version()` 返回 `[Object: null prototype] {}`（一个 GC 结构体），传 JS 字符串进去也报同样的错。

**这不是 MoonBit 的缺陷，是 WASM 的固有边界**：WebAssembly 的 MVP 和 GC 提案都
**没有跨边界的字符串类型**。所有语言都得自己适配——Rust 用 wasm-bindgen 生成胶水，
C 用手动指针+长度，Go 用 syscall/js 桥。本版本 MoonBit 不带 JS glue，所以自己写适配层。

**方案**：`core/src/engine_wasm_abi.mbt`，码点缓冲 + 索引寻址，只传 `Int`。
四引擎仍是纯函数，缓冲区只是传输通道，不含任何业务计算。

### 第二层：搬「码元」还是搬「码点」——第一次写错了

第一版 JS 侧用了 `charCodeAt` / `String.fromCharCode`（搬 UTF-16 码元）。
**56 项比对全部通过**。看起来完美。

但写单测时露馅了：

```
test "ABI 搬运：emoji 代理对按两个码元搬运" failed: `3 != 4`
```

`abi_len()` 返回 3，我以为是 4。于是写了个探针实测 MoonBit 的语义：

| 表达式 | 实测结果 | 含义 |
|---|---|---|
| `"加油💪".length()` | `4` | 按 **UTF-16 码元** 计数（与 JS 对齐） |
| `for ch in "加油💪"` | 迭代 **3** 次 | 按 **Unicode 码点** 迭代 |
| `Int::to_char(0x1F4AA)` | `Some(💪)` | 非 BMP 码点可以表示 |
| `Int::to_char(0xD83D)` | **`None`** | **代理区码元被拒**（不是合法标量值） |
| `Int::to_char(0x110000)` | `None` | 超出 Unicode 上限 |
| `Int::to_char(-5)` | `None` | 负数 |

**结论**：MoonBit 的 `Char` 是 32 位完整码点，`String` 迭代按码点、`length()` 按码元。
搬码元会让代理对的两半都被 `Int::to_char` 判为非法 → 替换成 U+FFFD → **emoji 直接丢失**。

**为什么 56 项比对没抓到**：因为前 56 项用的真实数据里没有非 BMP 字符，
而评测引擎的输出只有 5 个维度分数，不包含输入原文——emoji 被吃掉了也看不出来。
**测试通过 ≠ 正确，只说明测试没覆盖到。**

**修复**：契约改为搬**码点**。

```js
// JS 侧
for (const ch of s) w.abi_push(ch.codePointAt(0));      // 不是 charCodeAt
// ...读回
String.fromCodePoint(w.abi_read(i));                    // 不是 fromCharCode
```

并补了一条**能把整条往返链路验穿**的用例：用 `export_rlhf`（它的输出里原样包含
`prompt` / `chosen` / `rejected` 原文），喂 emoji / 生僻字（U+2000B、U+2A6A5）/ 全角数字 / 组合字符。

### 第三层：确认这个测试「有牙」

新用例通过后，我反过来验了一遍——**用错误实现（`charCodeAt`）跑同一个用例**：

```
错误(码元) 输出含 emoji : false
错误(码元) 输出含 U+FFFD: true
正确(码点) 输出含 emoji : true
正确(码点) 输出含 U+FFFD: false
错误版输出片段: "chosen":"加油！你一定能行 ����","rejected":"加油。"}]}
```

emoji 变成了 `����`。**用例确实能抓到错误，不是空测试。**

> 面试点：这是本条最有价值的地方。**「测试通过」和「测试有效」是两件事。**
> 写完测试后，把实现故意改错跑一遍——如果测试还绿，那测试就是摆设。
> 这里如果我只看「56 项全过」就收工，会带着一个会丢 emoji 的 ABI 交付，而且毫不知情。

## 坑 30：`Char::from_int` 已弃用，且边界必须做兜底

**现象**：
```
Warning (deprecated): Use `Int::unsafe_to_char` instead, and use `Int::to_char` for safe conversion
```

**修复**：不用 `unsafe_to_char`（会把非法值静默截断），用**安全的 `Int::to_char`** 并显式兜底：

```moonbit
fn abi_buf_to_string() -> String {
  let chars : Array[Char] = []
  for c in abi_buf {
    match Int::to_char(c) {
      Some(ch) => chars.push(ch)
      None => chars.push('\uFFFD')   // 负数 / 超范围 / 代理区 → 替换字符
    }
  }
  String::from_array(chars)
}
```

**理由**：这是**跨语言边界**。宿主是 JS，传什么都可能。用 `unsafe_to_char` 会让非法码点
静默变成某个乱码字符，宿主完全无从察觉；用 U+FFFD 则是**可见的失败**——
非法输入会在 JSON 输出里留下替换字符，宿主一眼能看见。

单测覆盖了 5 种非法输入（负数、超上限、孤立高代理、孤立低代理）+ 两端合法字符。

> 面试点：边界层「宁可可见地坏，不要静默地错」。`unsafe` 系列 API 在边界上是负资产。

## 阶段 5 · 遗留说明

- **生产路径仍是 JS 目标**。WASM 形态是「已验证可行的能力」，不是当前运行路径。
  后端 `import` JS 产物更简单；WASM 的价值在于「引擎可脱离 JS 运行时、以二进制形态嵌入任何宿主」。
  若后端要接 WASM，`tools/wasm_smoke.mjs` 里的 `wasmCall()` 就是现成的调用封装。
- **`--target wasm`（非 wasm-gc）未验证**。命令在当前环境被沙箱策略拒绝，改用 `--target wasm-gc` 跑通。
  wasm-gc 是超集，功能上不构成限制。
- **孤立代理字符无法跨边界**。JS 字符串若含非法 UTF-16（孤立代理），会被替换为 U+FFFD。
  正常文本（含 emoji、生僻字、组合字符）不受影响。这是码点表示法的固有取舍，已在代码注释与 README 中声明。
